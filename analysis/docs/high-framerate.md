# `high_framerate`: RT64 frame interpolation at the display's refresh rate

Vanilla presents exactly one rendered frame per game logic step, like original
hardware — the game's per-VI-retrace callback (`analysis/docs/
timing-and-mission-debug.md`) advances the world and submits one display list
per step, and `src/main/rcp_timing.cpp`'s pacing hooks hold each graphics task
for a modelled RCP frame time (36.5 ms default, ~27.4 fps) so the step rate
matches the console's. That means motion is only as smooth as ~27 fps no
matter how fast the host GPU is. RT64 (the renderer this port already uses)
ships its own frame-interpolation pipeline for exactly this case — synthesize
extra frames between two real game frames by interpolating their transforms —
but getting it to actually engage for this game needed two things RT64 alone
could not supply. This doc is the design record so neither has to be
re-derived.

## 1. How RT64's interpolation pipeline decides whether to run at all

Two independent pieces of state gate it, both read in
`deps/rt64/src/hle/rt64_workload_queue.cpp`:

- **`targetRate`** — the rate RT64 renders/presents at. Comes from
  `UserConfiguration::refreshRate`, which `src/main/rt64_render_context.cpp`'s
  `set_application_user_config()` (line ~124) already sets from
  `ultramodern::renderer::GraphicsConfig::rr_option` (`ultramodern`'s own
  translation layer — nothing new here). `rr_option = Display` asks RT64 to
  target the display's actual refresh rate instead of the console's.
- **`viOriginalRate`** — what RT64 believes the *game's own* logic rate is.
  Without this, RT64 has a target to render at but nothing to interpolate
  *from*, so it just presents each real frame once, same as vanilla, even with
  `targetRate` raised. RT64's own way of getting this is auto-detection:
  `VIHistory::pushFactor()`/`logicalRateFromFactors()`
  (`deps/rt64/src/hle/rt64_vi.cpp:164`) keeps a small ring of "how many VIs did
  the last N frames each span" and only returns a nonzero rate once every
  entry in the ring agrees — i.e. the game must present at a consistent 60/N
  cadence (60, 30, 20, 15, ... fps, one VI count every time).

Knife Edge fails that test structurally, not by bad luck. Its speed is
*defined* by how many VI retraces the RCP takes to finish a frame
(`rcp_timing.cpp`'s header comment), and our modelled RCP budget produces a
continuous ~27.4 fps — sometimes 2 VIs per frame, sometimes 3, depending on
exactly where the 36.5 ms budget lands relative to the 16.683 ms VI period.
The factor ring never agrees, `logicalRateFromFactors()` returns 0 forever,
and RT64's auto-detected `viOriginalRate` stays 0 — interpolation silently
never turns on, with no error and no log line to say why. This was confirmed
by reading the auto-detection code, not by trial and error against it.

The fix: don't rely on auto-detection. RT64 exposes a way to *tell* it the
rate directly, per display list, through its extended-GBI mechanism — the
same channel already used by things like `gEXSetViewport`/`gEXSetScissor` in
other RT64 ports. `gEXSetRefreshRate` (opcode `G_EX_SETREFRESHRATE_V1`,
`deps/rt64/src/gbi/rt64_gbi_extended.cpp`) calls `state->setRefreshRate()`
directly, bypassing the VI-factor heuristic entirely.

## 2. Injection design

### Why a prologue, not a GBI command in the game's own display list

The game's display lists are entirely generated by recompiled code we do not
modify (`CLAUDE.md`'s "Never hand-edit recompiler output" / "prefer fixing on
our side"). Rather than patching the game's DL-building functions to emit an
extra command, `RT64Context::send_dl()` (`src/main/rt64_render_context.cpp`)
already controls which address it hands to `app->processDisplayLists()` — so
instead of the game's own DL start address, it can point RT64 at a short
hand-built prologue that runs first and then branches into the game's
(unmodified) DL. The game's `OSTask` itself is never touched.

### The four-command prologue

Built once per submitted display list (when active) as raw words at scratch
RDRAM `0x7FF000` (see below):

```
p[0] = 0xE0525464u; p[1] = 0x10000064u;                                 // HOOK_OP_ENABLE, extended opcode 0x64
p[2] = 0x64000009u; p[3] = (uint32_t)rate & 0xFFFFu;                    // G_EX_SETREFRESHRATE_V1
p[4] = 0xE0525464u; p[5] = 0x20000000u;                                 // HOOK_OP_DISABLE
p[6] = 0xE0525464u; p[7] = 0x40000000u | (game_dl_addr & 0x0FFFFFFFu);  // HOOK_OP_BRANCH -> game DL
```

Each pair is one `DisplayList` entry (`{w0, w1}`), read by RT64's
`noOpHook()` (`deps/rt64/src/gbi/rt64_gbi_extended.cpp:334`). The game runs
F3DEX2, whose `G_SPNOOP` opcode is `0xE0` (`RT64_HOOK_OPCODE`); word 0's low
24 bits carry the magic `0x525464` (ASCII `"RT"`, then `0x64`) that marks a
NOOP as an RT64 hook rather than an ordinary no-op. Word 1's top 4 bits
(`p1(28,4)`) select the hook operation and the low 28 (`p1(0,28)`) carry its
value:

- **`ENABLE`** (op 1) with value `0x64` registers extended opcode `0x64` —
  until this runs, the interpreter doesn't recognize
  `G_EX_SETREFRESHRATE_V1` at all.
- **`G_EX_SETREFRESHRATE_V1`** (extended opcode `0x000009`, word 1's low 16
  bits = the rate) calls `state->setRefreshRate(rate)`
  (`deps/rt64/src/gbi/rt64_gbi_extended.cpp:118-121`).
- **`DISABLE`** (op 2) unregisters the extended opcode.
- **`BRANCH`** (op 4) retargets the interpreter's DL cursor to
  `game_dl_addr`, run through `RSP::fromSegmentedMasked()` with segment 0 = 0
  (true immediately after `rsp->reset()`, which `send_dl()` already calls at
  its top) — so the address is used as a plain physical offset, and game DLs
  are always 8-byte-aligned physicals under 8 MB, making the `0x0FFFFFFF`
  mask lossless.

**`DISABLE` runs before `BRANCH`, not after**, so the game's own display list
executes with extended-GBI parsing turned back off. That is what guarantees
opcode `0x64` (an otherwise-ordinary `G_SPNOOP` operand byte) can never
collide with anything the game's own DL emits — the extended interpretation
is only ever active for the 16 bytes of our own prologue.

No byte-swapping: these are stored as `uint32_t* p = (uint32_t*)(RDRAM +
0x7FF000)` and written as native-endian 32-bit stores, and RT64's own
`DisplayList` struct reads `w0`/`w1` the same way from the same RDRAM buffer
— that's exactly the layout the recompiled game's own `SW` instructions
already produce when they build a real DL, and exactly what `send_dl()`
already hands off for the game's own lists (no separate byte-swap step exists
anywhere on that path today).

### Scratch RDRAM: address and safety

Physical `0x7FF000` / vaddr `0x807FF000`, chosen from
`analysis/out/segment_map.md`'s conclusion that this is a **base-4-MiB
machine**: the highest byte the game's boot-time ROM loads ever write is
`0x80287C20` (§d), comfortably inside the low 4 MiB, and no code path assumes
an Expansion Pak. librecomp still allocates the full 8 MiB RDRAM buffer
regardless, so the entire upper 4 MiB is never touched by the game and is
free scratch space for the host side.

One-time safety check, run **strictly once, before the very first write**
(the words become nonzero by our own hand immediately after, so a second
check would be meaningless and is never attempted — the check is gated by a
function-local `static`, which C++ guarantees initializes exactly once): read
the 8 words at the scratch address; if any is already nonzero, something
else is using this region unexpectedly, and the injection fails safe —
prints one line (`[hfr] scratch RDRAM at 0x807FF000 unexpectedly in use;
high framerate interpolation disabled`) and permanently returns the
unmodified game DL address from then on, mirroring this project's general
fail-closed habit (e.g. the mouse-aim gates in `mouse-aim.md` §9.1).

## 3. Why the declared rate is a live measurement, not a constant

A single constant would be wrong for this game specifically because it runs
at two very different self-imposed rates depending on mode:
gameplay/in-mission cutscenes step at whatever the modelled RCP budget
produces (~27 fps at the current 36.5 ms default, but retunable via
`tuning.rcp_frame_ms` / `KE_RCP_FRAME_MS` — see `rcp_timing.cpp`), while
non-mission cutscenes are paced by the game's *own* hand-written limiter
(`func_801978C0`'s `osGetTime` busy-wait, 2,800,000 OSTime counts = 59.733 ms
= ~15 fps) which our pacing budget never overrides. Declaring a fixed ~27 Hz
to RT64 during a ~15 fps cutscene would make RT64 interpolate as if frames
were arriving twice as often as they really do — judder, not smoothness,
worse than presenting the real frames plain.

So `src/main/rcp_timing.cpp` tracks an EMA (alpha 0.25) of the wall-clock
interval between consecutive `ke_gfx_task_begin()` calls — the same
timestamp already used for RCP pacing, sampled once per real game frame
regardless of which of the two rates is currently in effect. Intervals
outside `[1, 250]` ms are excluded from the average entirely (not folded in,
and not used to reset it): under 1 ms is measurement noise, over 250 ms is a
load hitch or a paused frame, neither of which is a real cadence change.
`kerecomp::measured_game_frame_interval_ms()` (`src/main/support.h`) exposes
the current EMA; `RT64Context::maybe_inject_rate_prologue()` converts it to
an integer Hz (`std::lround(1000.0 / interval_ms)`, clamped to `[10, 60]`)
each time it runs, so the declared rate follows the game between its two
regimes automatically.

## 4. What was deliberately NOT done

- **No changes to `ultramodern`'s own VI thread.** It still runs its normal
  60 Hz VI loop unmodified; this feature works entirely through
  `rr_option`/`viOriginalRate`, which `ultramodern` and RT64 already expose
  for exactly this purpose.
- **Game logic pace is untouched.** `rcp_timing.cpp`'s pacing hooks
  (`ke_gfx_task_begin`/`ke_gfx_task_end`) are unchanged except for adding the
  read-only interval measurement; nothing about *when* the game is allowed to
  step was altered. Verified empirically (§5): measured game frames/s is the
  same with the flag on and off.
- **RT64's Manual refresh-rate mode is not exposed.** Only `Original` and
  `Display` are wired to the flag (`src/main/main.cpp`); `rr_manual_value`
  stays pinned at 0. A "target N Hz regardless of display" option is a
  plausible future knob but out of scope here.
- **No per-object `gEXMatrixGroup` tagging yet.** RT64's transform matching
  during interpolation is heuristic (`G_EX_ID_AUTO` — matches transforms
  frame-to-frame by comparing matrix data, not by any explicit game-supplied
  identity). This is expected to work correctly for ordinary moving geometry,
  but HUD elements (fixed screen-space overlays) or anything that
  teleports/respawns rather than moving continuously (a common failure mode
  for heuristic transform matching in other RT64-based ports) may show
  warping or smearing in the synthesized in-between frames. The documented
  escalation path, if the owner sees this hands-on, is tagging the relevant
  display-list matrices with an explicit `gEXMatrixGroup` id so RT64 matches
  by identity instead of heuristically — not attempted yet since it requires
  identifying which specific display lists draw the HUD/respawning objects,
  which is exactly the kind of RE work that should wait until there's a
  concrete artifact to chase.

## 5. Verification

### Headless (this session)

- Build: `cmake --build build-shim` — clean, only pre-existing unrelated
  warnings (`OptionCount` not handled in two `switch`es that predate this
  change).
- `./scripts/smoke_test.sh --rom ke_recomp_data/knifeedge.n64.us.1.0.z64
  --binary build-shim/KnifeEdgeRecompiled` — **PASS** (process alive, video
  rendering, audio non-silent) with the default `enhanced` profile (which now
  includes `high_framerate`).
- The `[hfr] declaring game logic rate N Hz to RT64 (display target M Hz)`
  line appears and changes as the EMA converges from a cold start (60 → 45 →
  34 → 29 → ... in the independent re-run) toward the *actual* measured
  cadence — which headless is ~20-23 Hz, **below** the 27.40 fps budget cap,
  because lavapipe's software rendering is itself slower than the budget.
  That is the EMA working as designed (it tracks reality, not the budget
  constant); on a real GPU that renders within budget it will sit at ~27.
  This log line is the primary headless-verification signal. The logged
  display target was consistently **0 Hz** in this environment: expected
  under a headless Xvfb — no real monitor for RT64 to query — and it means
  `targetRate` is 0, so **interpolation itself is genuinely off headless**.
  What the headless runs therefore prove is that the prologue parses
  harmlessly through RT64's hook path with real frames rendering behind it
  (the smoke test's 34k distinct colours come *through* the injected
  prologue), and that the declaration plumbing works; the owner's GPU run
  will be the first time interpolated frames are actually generated. Same
  category of headless-only limitation as the documented
  nativefiledialog/dbus and modal-message-box items elsewhere in this
  project's history.
- `--profile vanilla` produces **zero** `[hfr]` lines and (by code
  inspection: `maybe_inject_rate_prologue()`'s first check is
  `rr_option == Original`, which is what vanilla sets) never writes to
  scratch RDRAM — vanilla stays bit-identical to before this change.
- Game pace check (the constraint this feature must never violate): ran two
  12-second `KE_PERF=1` sessions back to back, `enhanced` (flag on) vs
  `custom` with every enhancement off (flag off) — reported `frames/s`
  (submitted display lists per second, i.e. the game's own logic step rate)
  was ~19.7-20.7 in both runs with matching per-interval display-list counts
  (within 1 of each other at every checkpoint). Interpolation is not
  perturbing game logic pace.

### Owner hands-on results (2026-07-31)

Verified on the owner's host GPU — the first run where interpolation
actually executed (headless never can, see above):

- **Works**: frame rate clearly higher, and most of the scene interpolates
  smoothly.
- **Artifacts confirmed** on exactly the class §4 predicted
  (per-frame-respawned effects mismatched by heuristic transform matching):
  the **lock-on effect** and the **bullet trails** from the player's gun
  warp/smear visibly.
- **Owner decision**: keep the feature, but out of the `enhanced` curated
  set — it is an experimental opt-in (custom profile) until per-effect
  `gEXMatrixGroup`/`gEXMatrixGroupNoInterpolate` tagging addresses the
  confirmed offenders. The lock-on effect and bullet trails are the first
  two targets for that work, whenever it happens; the likely treatment is
  opting them *out* of interpolation (render at game rate, no warp), which
  is the standard approach for particle-like effects in Zelda64Recompiled.

The checklist below is retained for reference / future re-verification
after any tagging work.

### Owner hands-on checklist (original, pre-verification)

- Does motion actually look smoother than the ~27 fps baseline at the
  display's real refresh rate (not just "the log line says a rate")?
- Any visible warping/smearing on HUD elements (health dial, S-BOMB gauge,
  reticle) or on enemies/objects that respawn or teleport rather than moving
  continuously — the heuristic-transform-matching risk from §4.
- Cutscene smoothness specifically (the ~15 fps regime) — confirm it tracks
  its own rate rather than the gameplay rate.
- Interaction with `full_height`/`widescreen` (both on by default in
  `enhanced` alongside this) — no reason to expect interference (this
  feature only affects DL start-address selection and RT64's presentation
  timing, neither of which those two enhancements touch), but not yet
  eyeballed together.
