# Game speed and mission start (2026-07-28)

Two bugs from real-hardware-GPU testing, fixed here:

1. **The game ran ~4x too fast.** Measured: 60.0 game frames/s where it should
   be ~15. Root cause: the game's logic step *is* its render step, gated on the
   RCP still being busy — and under RT64 a graphics task retires in ~0 game
   time, so the gate never fired.
2. **"GAME START" hung.** Two consecutive no-yield busy-wait loops that
   `find_functions.find_spin_loops()` did not detect, each wedging ultramodern's
   cooperative scheduler exactly like `boot-debug.md` §2's crash 2.

They do **not** share a root cause, but they meet in the same place: bug 1's
triage asked whether `find_spin_loops()` had *mis*classified a delay loop, and
the answer is that it had *missed* two polls. The detector was the suspect in
both investigations; it was innocent for bug 1 and guilty for bug 2.

Everything below is regenerated by `make -C analysis`, then
`deps/N64Recomp/build/N64Recomp config/knife_edge.us.toml` (exit 0, 1115
functions) and `cmake --build build-shim`. `scripts/smoke_test.sh` passes.

---

## 0. How the numbers were measured

`KE_PERF=1` (off by default) turns on the counters in `src/main/support.cpp`.
`kerecomp::perf_count_vi()` is called from `main.cpp`'s `vi_callback`, i.e. once
per ultramodern VI retrace; `kerecomp::perf_count_dl()` is called from
`RT64Context::send_dl`, i.e. once per graphics display list the game submits.
One line per wall-clock second goes to stderr:

```
$ DISPLAY=:99 SDL_AUDIODRIVER=dummy KE_PERF=1 ./build-shim/KnifeEdgeRecompiled --rom build/knife_edge.z64
[perf]  60.00 VI/s   60.00 frames/s  (total vi=2664 dl=2646)     <- before
[perf]  60.00 VI/s   15.00 frames/s  (total vi=2360 dl=587)      <- after
```

`frames/s` is the game's own step rate, because the game advances the world
exactly once per submitted display list (§1).

## 1. Bug 1 — the game's speed is defined by RCP frame time

### 1.1 What was ruled out first

* **`ultramodern`'s clocks are correct.** `ultramodern/src/timer.cpp` uses
  `counter_per_ms = 46'875`, i.e. 46.875 MHz, which is right for both
  `osGetCount` (COUNT increments at half the 93.75 MHz CPU clock) and
  `osGetTime`. `osSetTime`/`osGetTime`/`osSetTimer` in
  `librecomp/src/ultra_translation.cpp` pack the 64-bit values correctly.
  `speed_multiplier` is the compile-time constant `1`, and nothing overrides
  `ultramodern::get_speed_multiplier()`.
* **VI retrace delivery is correct.** Measured 60.00 VI/s. The game calls
  `osViSetEvent(&sc.interruptQ, 0x29A /* RETRACE_MSG=666 */, numFields)` at
  `0x800D20F0`, and both call sites of the scheduler-init function
  (`func_800CD740` / `func_800CD754`) pass `numFields = 1`, so one message per
  retrace is what the game asked for. `vi_thread_func`'s `remaining_retraces` /
  `cur_state->retrace_count` handling is therefore a no-op here.
* **The spin-loop hooks are not a speedup.** All 19 loops
  `find_spin_loops()` found were disassembled; every one is a condition wait
  (`while (*flag == 0)`, `while (SP/PI busy)`), not a timed delay.
  `yield_self_1ms` is ultramodern's own `wait_for_external_message_timed(…, 1)`,
  so a hooked loop still cannot leave before its condition is true.
* **The game does not time anything.** An exhaustive scan of every `code+data`
  segment for calls to `osGetCount` (`0x800E0B50`), `osGetTime` (`0x800E0C80`)
  and `osSetTimer` (`0x800E0D10`) finds callers only inside the boot segment's
  own libultra, plus exactly one game-side `osGetTime` at `0x80197AE0` — which
  is behind a debug flag (§1.3).

### 1.2 The actual mechanism

The game has no frame timer at all. It registers a per-retrace callback and
does one logic step per *rendered frame*:

```
func_800D1640(fn)                      -> stores fn at 0x800EBC00
func_800D2930 (thread, priority 50)    -> for each RETRACE_MSG:
        v0 = *(0x800EBC00);
        if (v0) v0( *(u32*)0x8013C280 );        // arg = graphics tasks in flight
```

`0x8013C280` is incremented when a task is queued (`func_800D1CB0`) and
decremented when the task-done thread `func_800D1730` receives its completion.
Every registered callback in the game starts the same way — the KEMCO logo
(`0x8017B1A8` in seg_0EF7C0), the title/attract screens, and the in-mission one
at `0x8019CF84`:

```
8019CF84  addiu  $sp, $sp, -0x20
8019CF88  sw     $a0, 0x20($sp)         ; a0 = tasks outstanding
8019CF8C  lw     $t6, 0x20($sp)
8019CF94  bgtz   $t6, <epilogue>        ; RCP still busy -> do nothing this retrace
8019CF9C  jal    func_800C3704          ; else: start a frame,
   ...                                  ;       run the world one step,
8019D09C  jal    func_800C3760          ;       submit one display list
```

So the game's speed is *defined* by how many VI retraces the RCP needs per
frame. On console a 3D frame spans several retraces and the callback no-ops on
the rest. Under librecomp + RT64 it spans none: `gfx_thread_func`
(`ultramodern/src/events.cpp`) calls `sp_complete()` the moment it dequeues the
task and `dp_complete()` the moment `RT64Context::send_dl` returns, so
`0x8013C280` was back to 0 at *every* retrace — 60 steps/s instead of ~15.

Measured before the fix: **60.00 frames/s at 60.00 VI/s**, i.e. one game step
per retrace, sustained for the whole attract loop.

### 1.3 Where the 59.733 ms budget comes from

The one game-side `osGetTime` call is a hand-written frame limiter at the end of
`func_801978C0` (in-game overlay, whole function gated on `*(0x8011D298) != 0`,
a developer profiling display):

```
80197AE0  jal   osGetTime               ; v0:v1 = OSTime
80197AE8  sw    $v0, 0x8011D268
80197AF4  sw    $v1, 0x8011D26C
80197B08  bnez  $t0, +5                 ; hi != 0 -> done
80197B0C  lui   $at, 0x2A
80197B10  ori   $at, $at, 0xB980        ; 0x002AB980 = 2,800,000
80197B14  sltu  $at, $t1, $at
80197B18  bnez  $at, -0xF               ; lo < 2,800,000 -> read the clock again
80197B38  jal   osSetTime(0, 0)
```

2,800,000 OSTime counts / 46.875 MHz = **59.733 ms**, i.e. the frame time the
developers paced their own debug view at — 3.58 VI periods, which quantises to
one step every 4 retraces (15 fps). That is exactly the "roughly 4x" that was
reported, from two independent directions.

### 1.4 The fix

`src/main/rcp_timing.cpp` gives a graphics task a minimum residency, and
`analysis/gen_syms.py`'s new `RCP_PACING_HOOKS` wires it into the game's
graphics task thread `func_800D25F0` (the one that receives from the task queue
at `0x801423EC`, does the double-buffer wait in `func_800D2768`, runs the task
and then posts completion):

| hook | vram | text |
|---|---|---|
| task start | `0x800D26D0` (`jal osSpTaskStartGo`) | `ke_gfx_task_begin();` |
| task end | `0x800D2728` (`jal osSendMesg`, the completion message) | `ke_gfx_task_end(rdram);` |

`ke_gfx_task_end` waits until `start + 59.733 ms` by looping `yield_self_1ms`,
which is the only legal way for a recompiled thread to burn game time: a plain
sleep would freeze ultramodern's cooperative scheduler. Both hook sites sit on
every path through the function (the `bnel` at `0x800D2710` that skips the
DP-done wait rejoins at `L_800D2724`, before the end hook). The audio task uses
a *different* thread (`func_800D2460`, queue `0x801423B4`), so audio is not
paced by this.

`KE_RCP_FRAME_MS` overrides the budget (`0` disables pacing); the chosen value
is printed at startup.

Why not in the shim alone: the only shim-side seam on the graphics path is
`RT64Context::send_dl`, and blocking there blocks ultramodern's single graphics
thread, which also drains `ScreenUpdateAction`s — presentation would stall in
57 ms bursts. Delaying the *game's* completion message instead leaves RT64
free-running.

### 1.5 Result

```
[perf]  60.00 VI/s   15.00 frames/s
[perf]  60.00 VI/s   15.74 frames/s
[perf]  60.00 VI/s   16.72 frames/s
```

15–17 frames/s (the spread is retrace quantisation: when the callback thread
has retrace messages queued it can start a frame between retraces, giving the
budget's own 16.74 fps rather than a quantised 15). VI stays at 60/s, so
presentation is unaffected.

## 2. Bug 2 — two undetected busy-wait loops

Both hangs were diagnosed the same way: `gdb -p <pid> -batch -ex "thread apply
all bt 25"` on the live process. In both, every ultramodern thread except one
sits in `osRecvMesg`, and the one that does not is spinning in recompiled game
code — the signature of `boot-debug.md` §2 (a game thread that never enters a
message primitive never drains ultramodern's external message queue, so VI
retrace / SP / DP messages stop being delivered and the whole runtime wedges).
`[perf]` confirms it from the outside: `60.00 VI/s  0.00 frames/s`.

### 2.1 First hang — selecting GAME START

```
Thread 7 "Game Thread 3":
#0  func_800E4CDC ()                 <- the LCG PRNG
#1  func_8017B0C0_0EF7C0 ()
#2  func_800CBA00 ()
#3  func_800C2450 ()                 <- main
#4  run_thread_function ()
Thread 6 "Game Thread 4":  osRecvMesg <- func_800D2930   (the retrace callback thread)
Thread 10 "Game Thread 19": osRecvMesg <- func_800D2214  (the scheduler thread)
... every other game thread likewise blocked in osRecvMesg
```

`func_8017B0C0` of seg_0EF7C0 (ROM `0x0EF7C0`, the overlay the front-end loads
into `0x8017B0C0` for this screen) is:

```
8017B118  jal   func_800D1640           ; register the per-retrace callback
8017B11C  addiu $a0, $a0, -0x4E58       ;   = 0x8017B1A8
8017B128  jal   func_800E4CDC           ; loop: v0 = rand()
8017B130  lui   $t0, 0x8012
8017B134  addiu $t0, $t0, -0x2E18
8017B138  sw    $v0, 0x0($t0)           ;       *(u32*)0x8011D1E8 = v0
8017B13C  lui   $t1, 0x8012
8017B140  lw    $t1, -0x2E4C($t1)       ;       t1 = *(u32*)0x8011D1B4
8017B144  beqz  $t1, 8017B128           ; while (screen result == 0)
```

`find_spin_loops()` rejected it on **one** rule: "the body contains no store".
The store here is `*(u32*)0x8011D1E8 = rand()` — publishing the PRNG state to a
fixed global while waiting, not walking a data structure.

**Fix (`analysis/find_functions.py`)**: a store is now allowed when its base
register is materialised from immediates inside the loop body, i.e. it writes an
absolute address. Every memcpy/fill/list-walk loop stores through a pointer the
loop itself advances, so those are still rejected — this is the same test the
detector already applied to loads. One extra rule keeps it honest: if the body
stores at all, every load must have a statically known address and no stored
address may also be loaded. That second clause exists because without it the
relaxation also matched the rejection sampler at `0x801D3A68`
(`do { *p = rand() & 0xF; } while (*p >= 10);`), which is computing, not waiting.

Detected loops go 19 → 20; hooks 13 → 14. The only new entry is
`seg_0EF7C0 func_8017B0C0 8017B128..8017B144`.

### 2.2 Second hang — during mission load

With the first hang fixed, GAME START → STORY → NORMAL → STAGE 1 → the Rumble
Pak notice all work, and the hang moves to mission init:

```
Thread 8 "Game Thread 3":
#0  func_8019CE04_1501A0 ()           <- no callee frame: spinning inside itself
#1  func_800CC690 ()
#2  func_800CBD04 ()
#3  func_800CBA00 ()
#4  func_800C2450 ()
Thread 7 "Game Thread 4":  osRecvMesg <- func_800D2930
... every other game thread blocked in osRecvMesg
```

`func_8019CE04` (in-game code overlay, ROM `0x1501A0`) is the mission loop:

```
8019CE5C  lui   $t0, 0x8012
8019CE60  addiu $t0, $t0, -0x2E28       ; 0x8011D1D8
8019CE64  lbu   $t1, 0xE($t0)
8019CE68  andi  $t2, $t1, 0x1
8019CE6C  beqz  $t2, 8019CF20           ; frame not due -> skip all the work
8019CE74  jal   func_800D1610           ; ... 40 instructions of per-frame work,
8019CF10  jal   func_800D1640           ;     ending by re-arming the callback
8019CF20  lui   $t4, 0x8012
8019CF24  lw    $t4, -0x2E4C($t4)       ; t4 = *(u32*)0x8011D1B4
8019CF28  beqz  $t4, 8019CE5C           ; while (screen result == 0)
8019CF3C  bnez  $t8, 8019CE5C           ; (0x8011BAD0 & 0x2000)
8019CF54  bnez  $t5, 8019CE5C           ; (func_800CB720() != 0)
```

When the frame-ready bit is clear the executed cycle is just
`lbu; andi; beqz; lw; beqz` — a pure poll with no yield. The loop *body*,
however, is 53 instructions containing five `jal`s and several branches, so
`find_spin_loops()` cannot prove anything about it: its whole design is that the
body is straight-line, which is what lets it conclude the loop can never reach
an OS primitive.

**Relaxing the detector to reason about paths was tried and rejected.** A
prototype that accepted a loop when *some* acyclic path through the body was a
clean poll found 40 extra loops, including `_bcopy` (4 of them), `memcpy`,
`_bcmp` (4), `alCopy`, `__osSumcalc`, `__osRepairPackId`, `_Ldtob` and a dozen
table scans — every one of which would have taken a `yield_self_1ms` per
iteration. That is a large, silent slowdown in exchange for catching one loop,
so the strict rule stands.

**Fix**: the loop is registered in `gen_syms.EXTRA_SPIN_YIELD_HOOKS`, the escape
hatch that already exists for exactly this (it was empty until now). All three
back-edges target `0x8019CE5C`, so a single hook there covers the loop.

To bound the whack-a-mole risk, every conditional back-edge in every code
segment whose body loads the screen-result word `0x8011D1B4` was enumerated and
checked against the hook list. Result: all eight menu/attract overlays are
covered by `find_spin_loops()`, `func_8019CE04` is covered by the manual entry,
and the only other matches are the front-end state machines
(`func_800CBA00` / `func_800CBB10` / `func_800CBD04`, whose "loops" call the
screen functions and therefore block inside them) and a `0xFFFF`-terminated
table scan at `0x801DC644` — no further gaps.

`GAME START → STORY → NORMAL → STAGE 1 (Amethyst Ravine, path A) → Rumble Pak

portraits, and gameplay runs: terrain, enemies, weapon fire, explosions, the

### 3.1 Input-method interference (found while play-testing on KDE)

Because the game samples the controller once per game frame, a keypress must be
held for at least one frame (~67 ms) to be seen — which is fine for a human but
puts held keys in the path of desktop "hold a key for the accent/IME picker"
features. On KDE those popups were swallowing holds outright.

The cause is on our side: **SDL2 enables text input during video init**, so the
window gets an input-method context (XIM/ibus/fcitx on X11, `text-input-v3` on
Wayland) even though the game never accepts text. The IME then consumes held
keys, and its popup takes focus, so `SDL_GetKeyboardState()` stops reflecting
what the player is holding.

`create_window` in `src/main/main.cpp` now calls `SDL_StopTextInput()` right
after `SDL_CreateWindow` and logs the transition. Verified under Xvfb/X11:

```
SDL video driver: x11
SDL text input (IME): on at window creation, off now
```

i.e. SDL really did leave it on. This does not affect `SDL_GetKeyboardState`,
which is what `get_input` reads — menus and gameplay were re-driven to stage 1
afterwards and `scripts/smoke_test.sh` still passes.

Two things this does *not* cover, if a desktop still intercepts holds:

* a compositor-level grab that never delivers the key to the application at all
  (test with `XMODIFIERS=@im=none QT_IM_MODULE= GTK_IM_MODULE=` in the
  environment; if that helps, the input method is still in the path);
* the underlying "a tap shorter than one frame is invisible" property, which is
  faithful to console (the N64 controller is also sampled once per frame) but is
  what makes scripted `xdotool key` taps unreliable. Latching presses between
  reads in `get_input` would remove it, at the cost of being more forgiving than
  hardware — deliberately not done.

### Open

0. **The target frame rate rests on two agreeing estimates, not a console
   capture.** The *mechanism* is proven (§1.2 — the game skips a retrace iff a
   graphics task is outstanding), but the numeric budget comes from the game's
   own debug limiter (§1.3) cross-checked against the reported "~4x". If a
   console or cycle-accurate-emulator capture ever becomes available, the only
   thing to change is `default_frame_ms` in `src/main/rcp_timing.cpp`.
1. **The 59.733 ms budget is a single global constant.** On console the RCP
   time varies with scene complexity, so a light 2D menu would have run faster
   than a mission. Modelling that would need an RDP cost estimate RT64 does not
   expose; `KE_RCP_FRAME_MS` is the knob if a per-scene number is ever wanted.
2. **`segment_map.md` §d open question 1 is still OPEN.** Nine descriptors
   declare BSS past the DMA'd image and no loader zeroes it, which only matters
   on a *re*load into a shared slot. §4 exercised the `0x801D21F0` slot a second
   time (mission 1 → mission 2) without a fault, but that is a single sample and
   the stale bytes left behind depend on how the mission was played (score,
   kills, RNG, live object state), so the question is not closed.
3. **Streamed music during a mission is unverified.** `func_800CD800`'s
   destination is still the untraced runtime pointer at `0x80149AEC`
   (`segment_map.md` §d open question 5). Audio is non-silent in-mission
   (`scripts/smoke_test.sh` passes) but the streamed tracks specifically were
   not identified in the output.

## 4. "Stuck on the post-mission results screen" — not a hang (2026-07-28)

A play-tester completed mission 1, saw the results screen (SCORE / PLAYER 1
STATUS / ENEMY DEFEAT % / VULCAN LEVEL / HIT %, drawn over the darkened mission
terrain) and reported that the game sat there permanently with input doing
nothing and no console output.

**It was never a hang.** The binary from that run does not print the
`SDL text input (IME): ...` line, so it predates §3.1's `SDL_StopTextInput()`
fix: the desktop's input method was swallowing the held button. A later build
completed mission 1 and reached stage 2 cleanly. No code change was made for
this report; §3.1's fix already covers it.

### 4.1 The results screen has no timer — it exits only on a button

Established statically, and it is what makes the "dropped input" explanation
sufficient. The screen is `func_80193A34` in the in-game code overlay
(`seg_1501A0`), reached from the mission sub-state dispatcher `func_800C7E1C`
(jump table at `0x800ED414`, entry 20 = `0x800C7E7C`) once the script command at
`0x80192434` sets bit 1 of the flag byte `0x8011D1E2`:

```
80193A40  jal   func_800C7AD0 / func_800C7A60   ; fade the terrain down
80193A7C  jal   func_801957BC/8C8/A60           ; draw the table (by game mode)
80193AA4  jal   func_80193E94
80193AAC  lw    $t6, 0x8011D1B4                 ; screen result
80193AB4  bnez  $t6, 80193B2C                   ; already set -> do nothing
80193AC0  lw    $t7, 0x8011D1C4                 ; player count
80193AC8  beqz  $t7, 80193B2C
80193AE8  lhu   $t0, 0x8011BE22 + i*0xA         ; controller i, held buttons
80193AEC  andi  $t1, $t0, 0xB000                ; A | B | START
80193AF0  beqz  $t1, next
80193AF8  jal   func_800C32CC
80193B08  sw    $t2, 0x8011D1B4                 ; result = 1  (mission complete)
```

There is no frame counter, no `osGetTime`, no auto-advance: `0xB000` is
`A (0x8000) | B (0x2000) | START (0x1000)` and the word at `0x8011BE22 + i*0xA`
is the *held* button state that `func_800C7458` refreshes once per game frame.
So the screen waits forever, by design, and a swallowed hold is
indistinguishable from a wedged process from the outside.

Two further details worth having on record, because both are "waiting, not
hung" states that look identical on screen:

* Once a button *is* seen, `0x8011D1B4` becomes 1 and the `bnez` at `0x80193AB4`
  makes every later press a no-op — so a genuinely stuck completion would also
  report "input does nothing".
* The mission loop `func_8019CE04` does not return the moment the result is set.
  Its exit needs all three of `result != 0`, `!(*(u16*)0x8011BAD0 & 0x2000)` and
  `func_800CB720() == 0`, and `func_800CB720` is
  `func_800CF488(2) + func_800CF488(1)`, i.e. the number of sound/sequence
  players still active (`0x80149CF4` count, list at `0x80149CFC`, stride
  `0x120`). The game therefore holds the results screen until the mission-end
  audio has finished. A sequence player that never reports idle would freeze the
  screen with input dead — the same picture again.

### 4.2 How mission completion was reproduced without beating the boss

Stage 1 only ends when its boss is killed, which is not automatable, so the
completion path was driven by firing the game's own "mission cleared" script
command from the shim. Recorded here because it is the cheap way to test any
mission-end path; the scaffold itself was **removed** and is not in the tree.

The command is the case at `0x80192434` of the script interpreter
`func_801922A8`:

```
*(u8*)0x8011D1E2 |= 2;      /* show the results screen */
*(u8*)0x8011D1E5  = 0;
*(u32*)0x8011D1F0 = 0;      /* selects func_80193A34 over func_80196810 */
*(u32*)0x8011D204 = 0;  *(u32*)0x8011D200 = 0;  *(u32*)0x8011D1FC = 0;
func_800D1680();
```

Writing those six globals from `ke_gfx_task_end()` in `src/main/rcp_timing.cpp`
(which already runs once per game frame and has `rdram`) N frames after
`ke_overlay_dma()` sees a load into the shared mission slot `0x801D21F0` puts
the results screen up in seconds. `rdram` addressing is
`*(uint32_t*)(rdram + (vaddr & 0x0FFFFFFF))` for words and `^ 3` for bytes.
Optional invulnerability for longer runs: hold `*(u32*)0x8011D464` (player 1
health %, the value `func_801752D8` prints in the HUD) at 100.

With that, `xdotool` reached the results screen, dismissed it with `x` (A),
advanced through the STAGE 2 / PATH A select and the Rumble Pak notice, played
mission 2 (Dead City) and reached *its* results screen — so the completion
transition, the score accumulation in `func_800CC4D0`, the stage counter at
`0x8011D1BC`, the intermission screen `func_800CC8D0` and a second load into the
shared `0x801D21F0` slot all work.

**One latent hazard was found and is deliberately left unfixed.** Two of five
forced completions died with

```
Failed to find function at 0x8019CF84
```

(`librecomp`'s `get_function`, which `std::exit()`s). `0x8019CF84` is the
mission's per-retrace callback, registered in `0x800EBC00` by `func_800D1640`
and dispatched by `func_800D2930`'s `jalr`. It deregisters itself
(`func_800D1640(0)` at `0x8019D0E0`) only under the same three-way condition the
mission loop uses, and the callback runs at most once per RCP frame (~60 ms
under §1.4's pacing) while the mission loop re-tests it every ~1 ms — so the
main thread can leave the loop and reach `func_800CC8D0`'s first DMA while the
pointer is still live. On hardware that is harmless: `func_800CC8D0`'s four
images only reach `0x8018DBF0`, so the bytes at `0x8019CF84` are *not*
overwritten and the callback stays valid for the frame or so until it retires
itself. `ke_overlay_dma()` in `src/main/register_overlays.cpp`, however, grows
the unload to whole-section granularity and drops all of `seg_1501A0`
(`0x8016D6F0..0x801A0C50`), so that still-intact code becomes unresolvable.

The fix would be to re-register a section this DMA only *partially* covers,
before loading the incoming sections so theirs win for any address both claim.
It is not applied because the fault has only ever been produced by the forced
trigger above — a natural completion sets up the mission-end audio, which
changes the interleaving — and because re-registering makes an address in the
overwritten head resolve to the old section's function instead of the new bytes.
If `Failed to find function at 0x8019CF84` is ever seen in normal play, that is
the change to make.

### 4.3 Diagnostic lesson

A screen that waits on input is indistinguishable from a hang once input is
being dropped: same frozen picture, same dead controller, same silent stderr.
The two are told apart from the outside by

* the `SDL text input (IME): on at window creation, off now` line at startup —
  its **absence** means the build predates §3.1 and the input path is suspect
  before anything else is;
* `KE_PERF=1` — a wedged game thread reads `60.00 VI/s 0.00 frames/s`, while a
  screen that is merely waiting keeps its 15–17 frames/s;
* `gdb -p <pid> -batch -ex "thread apply all bt 20"` plus `top -H -p <pid>`,
  which separate a spinning thread from an all-idle deadlock (§2).

Check the first two before reaching for the third.
