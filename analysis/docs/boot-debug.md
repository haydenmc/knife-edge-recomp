# First-boot debugging log (2026-07-28)

Starting point: the recompiled build ran its own code but died in OS init with

```
run_thread_function -> func_800CD710 -> func_800D1FA0 -> func_800DA180 -> func_800DA2FC   SIGSEGV
```

End state: the game boots, renders, reaches its title screen and runs the whole
attract sequence (KEMCO logo -> title -> story text -> Mars canyon flythrough ->
space-station cinematic) in a stable loop. A 200 s soak run finished with no
crash and no assertion.

Everything below is regenerated by `make -C analysis` (verified byte-identical
after `make -C analysis clean`), then
`deps/N64Recomp/build/N64Recomp config/knife_edge.us.toml` (exit 0, no
unresolved jal targets, 1115 functions) and `cmake --build build-shim`.

## 1. Functions named (analysis/ident_libultra.py `CURATED_NAMES`)

A new curated override table runs after the n64sym gates. Every entry carries a
structural gate (`calls` / `called_by` / `refs` / `words` / `loads_io`) that is
re-checked on each run, so a boundary regression fails loudly in
`analysis/out/libultra_report.txt` instead of silently mislabelling.

An MMIO sweep of the boot segment (lui immediates 0xA000/0xA404/0xA408/0xA410/
0xA430/0xA440/0xA450/0xA460/0xA480) finds 30 functions. 29 were already named;
after this pass **zero unnamed boot functions touch RCP MMIO**, and the
`[patches].stubs` escape hatch (`ident_libultra.STUB_FUNCS`, plumbed through
`gen_syms.py`) is empty.

### Deliberately left unnamed

* **0x800DA800** - reached only from `osSpTaskLoad`(0x800DA91C), which librecomp
  reimplements, so it is dead. It bcopies the 0x40-byte `OSTask` into a static
  and converts the pointer fields with `osVirtualToPhysical`; no MMIO.
* **0x800DC460**, **0x800E4CDC**, **0x800E4CDC**-adjacent leaves - no MMIO,
  ordinary code (0x800E4CDC is the LCG `x = x*0x4E6D + 0x3039` PRNG).
* Known cosmetic mislabel: **0x800DB860 / 0x800DB8B0** are named
  `__osSpRawReadIo` / `__osSpRawWriteIo` but are really `__osSiRawReadIo` /
  `__osSiRawWriteIo` (they call `__osSiDeviceBusy`(0x800E1380) and are called
  from `__osInitialize_common`'s PIF clock-rate read). Both name pairs are in
  `ignored_funcs`, so nothing is emitted either way and behaviour is identical.
  Left alone because the `MANUAL_NAMES` gate for `osInitialize` keys off the
  current name.

## 2. Crash 2 - cooperative-scheduler deadlock on a busy-wait

After the naming fix the game got through OS init (PI/VI managers up, 8 threads
created, RT64 initialised) and then froze with a black screen.

`func_800D2B40` is `do { t7 = *(u32*)0x8013C280; } while (t7);` - it waits for
the outstanding-task counter that `func_800D1730` decrements when a task
completes. ultramodern delivers messages posted by native threads (VI retrace,
SP/DP done, PI) through an *external* queue that is only drained inside
`osSendMesg`/`osRecvMesg`/`osJamMesg` or when a game thread blocks
(`ultramodern/src/mesgqueue.cpp`, `scheduling.cpp`). A recompiled thread that
spins on memory never drains it, so the whole runtime wedges - measured: 2683
retrace messages enqueued, 0 delivered, `validCount` stuck at 0 on every queue.
On hardware the same loop is preempted by the RCP interrupt handler.

N64Recomp already rewrites the unconditional `b .` form into `pause_self()`
(`src/recompilation.cpp:495`); the conditional form is not handled.

**Fix**: `analysis/find_functions.py:find_spin_loops()` detects no-yield polling
loops and `analysis/gen_syms.py` emits one `[[patches.hook]]` per hit calling
`yield_self_1ms(rdram)` (declared via `recomp_include`) at the top of the loop
body. `yield_self_1ms` drains the external queue, waiting at most 1 ms, then
hands execution to any higher-priority ready thread - exactly what the interrupt
would have done.

Detector rules (a poll, not a data loop):

* backward branch inside one function, body <= 12 instructions;
* body contains no store, no other branch, no `j`/`jr`/`jalr`;
* a `jal` is allowed only if the callee is a **leaf** (a leaf can never reach
  `osRecvMesg` and friends) *and* no argument register a0-a3 is written from a
  non-constant source - that is what separates `while (!flag) rand();` from
  `while ((x = p->next)) { unlink(x); link(x); }` (`_collectPVoices`, correctly
  rejected);
* at least one load, and every load's base register is either never written in
  the body or materialised from immediates inside it (a memcpy/strlen loop
  advances its pointer, so it is excluded).

19 loops are found; the 6 that carry libultra names
(`__osPackReadData`, `__osViInit`, `osPiRawReadIo`, `osPiRawStartDma`,
`osEPiRawWriteIo`, `osEPiRawReadIo`) are skipped because N64Recomp emits no body
for `ignored_funcs`/`reimplemented_funcs`. The remaining 13 become hooks:
`func_800CD710`, `func_800D2B40`, and one per menu/mission overlay image
(the KEMCO/attract screens all spin on the flag at 0x8011D1B4).

`analysis/gen_syms.EXTRA_SPIN_YIELD_HOOKS` is the manual escape hatch; it is
currently empty.

## 3. Crash 3 - "Cannot partially unload section"

```
Cannot partially unload section
  rom: 0x000BA450 size: 0x000126B0 loaded_addr: 0x8017B850
  unloaded_ram: 0x8017B0C0 unloaded_size : 0x00000980
```

Two independent bugs, both in the overlay bookkeeping, both fixed in
`src/main/register_overlays.cpp`:

1. **librecomp's first-1MB registration is wrong for this game.**
   `librecomp/src/recomp.cpp:486` does `load_overlays(0x1000, entrypoint, 1MB)`
   before calling the entrypoint. Six of Knife Edge's code segments (rom
   0x02FC30, 0x03D600, 0x041650, 0x0BA450, 0x0EF7C0, 0x0F4810) live *inside* the
   first megabyte, so they were registered at `rom_addr + 0x800C1400` - e.g.
   seg_0BA450 at 0x8017B850, which is exactly the bogus `loaded_addr` above.
   Nothing ever unloads those.
   **Fix**: `kerecomp::reset_boot_window_overlays()` drops every non-boot
   registration from that window. It is called from a new entrypoint wrapper
   (`knife_edge_entrypoint` in `src/main/main.cpp`, installed as
   `GameEntry::entrypoint`), which runs after `init()` and before any game code.

2. **Whole-section unload granularity.** Eight menu overlays share VRAM
   0x8017B0C0 with sizes from 0x980 to 0x42C0, so a smaller image landing on a
   larger resident one only partially covers it, which librecomp treats as
   fatal. **Fix**: the DMA hook now calls `ke_overlay_dma()` instead of
   `unload_overlays(); load_overlays();`. It keeps a shadow copy of librecomp's
   `loaded_sections` (not exposed) and grows the unload range to whole-section
   granularity before delegating. Dropping the whole displaced section is the
   closest representable behaviour: its tail bytes survive in rdram exactly as
   on hardware, and the game never calls into a half-overwritten overlay.
   The shadow's overlap predicate deliberately mirrors librecomp's, **including
   its inclusive end test** (`ram_addr + size >= loaded_ram_addr`) - a section
   starting exactly where the unloaded range ends still counts, and using the
   strict form here caused a second, later abort at
   `unloaded_ram 0x801726A0 size 0x8A20` vs a section at 0x8017B0C0.

## 4. Crash 4 - audio microcode task killed the process

```
No RSP microcode registered for task type 2 yet
Failed to execute task type: 2
Exiting with exit status '1'.  (ultramodern/src/events.cpp:282)
```

`get_rsp_microcode()` returned `nullptr` for the audio task (`M_AUDTASK`), and
`recomp::rsp::run_task` treats that as fatal. RT64 handles graphics tasks
internally, so this was the first non-graphics task the game submitted.

**Fix** (`src/main/main.cpp`): unknown task types now get a no-op ucode that
returns `RspExitReason::Broke`, i.e. the RSP "finishes" and librecomp sends the
SP-done message the game is blocked on. No samples are produced - audio output
is not wired up at all yet - but the game is no longer killed.

**Superseded 2026-07-28** by `analysis/docs/audio.md`: the audio ucode is the
stock libultra `aspMain` (ROM `0x23EC0`, 0xE20 bytes, IMEM `0x1080`), it is now
recompiled by RSPRecomp (`config/aspMain.us.toml` ->
`generated/us/rsp/aspMain.cpp`) and `get_rsp_microcode` returns it for
`M_AUDTASK`. The no-op above is kept only as the fallback for task types that
are neither `M_GFXTASK` nor `M_AUDTASK` (this game submits no such task).

## 5. Blocker 5 - no controllers attached

The first rendered frame was the KEMCO logo overlaid with **"THERE ARE NO
CONTROLLERS ATTACHED TO THE NINTENDO 64"**, and the game stopped there:
`ultramodern::input::callbacks_t` was left empty, so librecomp's HLE'd
`osContInit` reported zero devices.

**Fix** (`src/main/main.cpp`): a minimal keyboard input backend - `poll_input`,
`get_input`, `set_rumble`, `get_connected_device_info` - reporting controller 0
as a plain Controller with no pak. Bindings: X=A, Z=B, LShift=Z, Enter=Start,
arrows=D-pad, Q/E=L/R, IJKL=C-buttons, WASD=analog stick. A remappable binding
UI is still TODO.
